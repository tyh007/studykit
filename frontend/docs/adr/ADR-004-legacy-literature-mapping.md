# ADR-004: Bringing the old literature hub into Research projects

- Status: Accepted (P7a, 2026-11-27)
- Context: v0.5 refactor plan §4.3 and §5 (P7); ADR-003

## Context

The v0.3 literature hub (`components/literature/`, `lib/literature-*`, backend `routes/literature-*`, `paper-*`) has been unreachable from the v0.4 interface. People who used it still have data there: projects, papers with server-side PDFs, PDF highlights, notes, paper relations, AI-extracted summaries and custom summary columns, and canvases. The plan is to merge what is useful into the Research workbench and then delete the old code, but **only after the data mapping is defined and tested**. This ADR is that mapping.

What the hub stored and where:

| Data | Where | Reachable from |
|---|---|---|
| Literature projects, papers (metadata, `extracted_data`, reading status, importance) | backend Postgres; mirrored in Dexie `literatureProjects` / `literaturePapers` for local workspaces | `getDataApi()` in both workspace kinds |
| Paper PDFs | backend storage (`/api/literature/papers/:id/download`) | sync workspaces |
| PDF annotations (`paper_annotations`: highlight / underline / ink, page, optional text) | backend | sync workspaces |
| Paper notes (`paper_notes`), paper relations (`paper_relations`), custom summary columns (`literature_custom_fields`) | backend | sync workspaces |
| Canvases (`literature_canvases`, nodes, edges, scenes) | backend | sync workspaces |
| Reading lists | backend, tied to Study modules and citation items, not to literature projects | Study |
| AI chat (`AIChatPanel`) | not stored | — |

## Decision

A one-step import per legacy project, offered on the Research home page while any legacy project has not been brought in. It writes canonical Research records with `authorType: 'imported'` and deterministic ids derived from the legacy ids, so running it again adds what is new and never duplicates or overwrites what the user has changed since.

| Legacy | Becomes | Rule |
|---|---|---|
| Literature project | `ResearchProject` `lp_<id>` | name; description → the project's question (`livingBrief`); kind `review`. |
| Paper (not trashed or deleted) | `Work` (id from DOI / title / authors / year, as everywhere else) + `WorkAsset` `lit_<paperId>` of kind `linked-file` | A Work that already exists (same DOI) is reused: the project is added to it and its fields are left alone. New Works take title (or the file name), authors (split on `;`), year, journal → venue, DOI, abstract, reading status, importance (0–5). The linked file opens the old PDF through the existing reader path (sync workspaces). |
| Highlight or underline **with text** | `Evidence` `lit_ann_<id>`, status **candidate** | Quote = the highlighted text; locator = page on the linked file. Interpretation stays empty, so it backs nothing until the user checks it at the page, exactly like an excerpt an agent proposes. Note: "Highlighted in the old literature hub". |
| Highlight without text; ink drawings | not imported | Counted and reported. There is no quote to check; drawings have no meaning outside the page. |
| Paper note | statement in an `Output` "Notes from the old literature hub" (`lit_notes_<projectId>`), one section per paper | `origin: imported`, status draft. The user's own words, kept in Writing where they can be moved into the argument. |
| Paper relation | statement in the same Output, section "How the papers relate" | "A extends B: description". Only relations between papers of the same project; each once. |
| `extracted_data` and custom columns | one assistant message per paper in a private conversation "AI summaries from the old literature hub" (`lit_ai_<projectId>`) | These were generated by AI and never checked, so they stay AI text: readable in the AI panel, labelled, outside the argument and the ledger. Custom column values are shown under the column's name. |
| Canvases | not imported in P7a | Decided with the canvas unification in P7b. |
| Reading lists | not imported | They belong to Study modules, not to literature projects; they stay where they are. |
| `full_text` | not imported | Derived from the PDF; the reader reads the PDF itself. |

Where the hub is only partly available (a local workspace has projects and papers but no notes, highlights, relations or columns), the import brings what is there and says what it couldn't reach.

## Consequences

- Nothing the hub held is silently dropped: every category is either mapped, reported as skipped with a reason, or kept in place (reading lists).
- Imported highlights and AI summaries enter as unchecked, so the ledger's rule holds: only what the user checked counts.
- The provenance report counts imported paragraphs as "imported" and imported excerpts like any other until checked.
- Deleting the old frontend code (P7b) must wait for: the mapping tests passing, the reader reaching parity for PDF highlights (P2 already turns highlights into excerpts), and a decision on canvases. The backend routes stay readable until the import has been available for a release, because the import reads through them.
